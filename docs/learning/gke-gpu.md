# NVIDIA GPU on GKE

## Week 3 outline

The current Free Trial excludes GPUs. On 2026-11-17, the project had zero global GPU quota, despite a regional limit of one L4 and one T4 in `europe-west3`. The Compute catalog included L4 in `europe-west3-a` and `-b`, T4 in `-b`, and H100 variants in `-a` and `-c`. Catalog entries describe supported locations. Quota and real-time capacity are separate constraints. This exercise uses read-only checks and a CPU simulation. Any GPU provisioning belongs to a separately approved, GPU-enabled environment. [Free Trial terms](https://docs.cloud.google.com/free/docs/free-cloud-features), [GPU locations](https://docs.cloud.google.com/compute/docs/regions-zones/gpu-regions-zones)

1. **Eligibility and capacity.** Inspect the zone's accelerator and machine-type catalogs, regional on-demand or Spot quota for the exact accelerator and VM family, global `GPUS_ALL_REGIONS`, associated CPU quota, and GKE version support. Check account eligibility before considering capacity, reservations or provisioning. For read-only inspection, use `gcloud compute accelerator-types list`, `gcloud compute regions describe europe-west3 --format=json` and `gcloud compute project-info describe --format=json` with the explicit project flag. [Standard GPU quota and provisioning](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/gpus)
2. **Compare capacity ownership.** Sketch a Standard pool dedicated to L4 with a compatible G2 shape, regional quota, COS and GKE-managed NVIDIA drivers. Consider a zero-minimum autoscaled GPU pool alongside system CPU capacity. Sketch the Autopilot equivalent using workload GPU requirements, supported accelerator selectors, default or requested driver version, and GKE provisioning. Check current hardware-specific scheduling and billing rules. [Standard GPU pools](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/gpus), [Autopilot GPUs](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/autopilot-gpus)
3. **Future smoke workload.** Design a single-completion Job with a pinned NVIDIA CUDA image compatible with the driver, a deadline and low retry limit. Run `nvidia-smi -L` and a small CUDA computation. Request one `nvidia.com/gpu` in limits, plus compatible CPU and memory requests. Select L4 via the GKE accelerator label or node affinity. Allow the pool's GPU taint where required. A toleration permits placement and affinity selects it, while the device plugin advertises allocatable devices. In the CPU simulation, use the existing Standard lab's `cloud.google.com/gke-nodepool=default-pool` or a hostname selector and change the selector to an absent value to reproduce Pending. Use a local disposable cluster with a tainted worker to test the toleration case without adding cloud nodes.
4. **Drivers, sharing and telemetry.** Identify separate owners for drivers, NVIDIA device plugin, and DCGM metrics. GKE can handle driver and device integration. NVIDIA GPU Operator bundles several host components. On Standard, avoid dual ownership and verify the chosen version and deployment configuration before delegating components to the operator. Autopilot host access constraints affect which agents can run. Compare time-slicing (logical sharing, no MIG-style hardware isolation) with MIG partitioning where the exact accelerator, profile and mode support it. Inspect utilization, memory and errors through GKE GPU metrics or DCGM and account for collector cost and cardinality. [Time-sharing](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/timesharing-gpus), [MIG](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/gpus-multi), [GPU metrics](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/dcgm-metrics), [NVIDIA GPU Operator](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/overview.html)
5. **Troubleshoot in order.** For Pending, inspect admission, scheduler events, selectors, taints, sharing mode and declared GPU resources. For no scale-up, inspect GKE autoscaler logs, job fit, pool limits, model-specific and global quotas, CPU quotas and zonal stockouts. Track time from workload admission to node creation, Ready and device advertisement. For a Ready node with missing devices, check driver install and plugin logs in Standard, compare capacity and allocatable, and test device visibility from the workload. Treat CUDA compatibility, MIG profile, driver faults and application GPU-memory exhaustion as distinct from provisioning failures.
6. **Control idle cost.** Estimate the provisioned node, accelerator or bundled machine, disks, telemetry, network and GKE fees. Include startup, driver readiness, image/model loading and scale-down lag. For batch, evaluate Kueue admission quotas, ResourceFlavors and queueing before releasing work to the scheduler. For future vLLM serving, evaluate model fit, cold start and request-queue or throughput metrics before choosing replica floors. HPA adjusts replicas and can drive node provisioning indirectly. [GKE pricing](https://cloud.google.com/kubernetes-engine/pricing), [Kueue on GKE](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/kueue-intro)
7. **Cleanup design.** Delete the approved workload and verify scale-down. In a future environment remove the dedicated Standard GPU pool or disposable cluster with explicit approval. For Autopilot confirm provisioned accelerator capacity is released. Compare independent GKE and Compute inventory for remaining nodes, disks and networking, then check delayed billing data and any separate reservation commitments. Reuse the [Standard cleanup procedure](gke-practical-lab.md#6-approved-deletion-and-independent-verification) for the CPU control run.

Learning check: Explain how quota, available capacity, an advertised device, and an idle but provisioned accelerator would appear in four different checks.
