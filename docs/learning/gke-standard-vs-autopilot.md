# GKE Standard and Autopilot

| Decision | Standard | Autopilot |
| --- | --- | --- |
| Control plane | Google operates the API server and etcd. A zonal cluster has a single-zone control plane. Regional Standard replicates it across zones. Putting zonal worker pools in multiple zones does not make the control plane regional. | Google operates a regional control plane. Plan workload HA separately with replicas, topology spread, zonal capacity and compatible storage. [Regional clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/regional-clusters) |
| Nodes and placement | Choose node locations, machine types, boot disks, identities, images, labels and taints. With regional pools, verify whether node counts and autoscaling bounds apply per zone or across the pool. | GKE creates and removes nodes from admitted Pod requests and scheduling constraints. ComputeClasses select compute characteristics and, for custom classes, ordered priorities. Inspect Node objects and events for placement. Node SSH and customer node administration are restricted. [GKE modes](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/types-of-clusters), [ComputeClasses](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-built-in-compute-classes) |
| Capacity scaling | Cluster Autoscaler sizes existing autoscaled pools for schedulable requests. Node auto-provisioning can create pools for new hardware or placement needs. Standard also supports ComputeClass-scoped pool creation on supported versions. | GKE owns the node scaling configuration and may remove workload capacity when it is no longer needed. Observe asynchronously. Infrastructure, system activity and hardware-specific billing can have different lifetimes from the app's replicas. [Cluster Autoscaler](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-autoscaler), [Node auto-provisioning](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/node-auto-provisioning) |
| Workload scaling | HPA changes replica counts. CPU utilization targets are relative to CPU requests. Missing requests can make utilization undefined. Scheduler fit and Cluster Autoscaler evaluate requests and placement constraints. | The same HPA and scheduler concepts apply to the **admitted** Pod. GKE defaults missing requests, adjusts values for minimums and CPU-to-memory ratios, and can reject unsupported configurations. Compute class, hardware and bursting support affect requests and limits. [Horizontal Pod Autoscaling](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/horizontalpodautoscaler), [Autopilot resource requests](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-resource-requests) |
| Versions and disruptions | Release channels govern version rollout. Inspect control plane and node versions separately. Configure node auto-repair and supported node upgrade strategies, including surge settings and quota headroom. | Release channel enrollment and automatic upgrades apply. Google manages node repair and replacement. Maintenance policies give scheduling control over eligible maintenance. Use PDBs, readiness probes and replica placement. Plan for repairs, emergencies and other involuntary disruptions outside windows. [Release channels](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/release-channels), [Node auto-repair](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/node-auto-repair), [Maintenance policies](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/maintenance-windows-and-exclusions) |
| Networking | Choose VPC-native alias IP networking, and choose Dataplane V2 when creating the cluster. Budget subnet primary space for nodes and secondary space for per-node Pod CIDR blocks. Service addresses can use a secondary subnet range or the supported GKE-managed range. | VPC-native and Dataplane V2 are standard. Dataplane V2 uses eBPF and includes Kubernetes NetworkPolicy enforcement. Workloads still need policies to restrict traffic. VPC firewall rules and endpoint access are separate controls in both modes. [IP planning](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/alias-ips), [Dataplane V2](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/dataplane-v2) |
| Workload identity | Enable Workload Identity Federation for GKE on the cluster and relevant pools. Node service account permissions are a separate decision. | Workload Identity Federation is always enabled. Both modes require explicit IAM grants for workloads that call Google APIs. [Workload identity](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity) |
| Host access | Privileged containers, DaemonSets, host namespaces and host mounts are possible subject to admission, node image and policy. Standard fits agents requiring kernel or device access. | DaemonSets are supported within restrictions. Ordinary users cannot run privileged Pods, use host namespaces or mount arbitrary writable host paths. Supported allowlisted privileged workloads and restricted read-only log mounts are exceptions. [Autopilot security](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-security) |
| Troubleshooting | Start with Pod events, GKE operations, Cloud Logging and Monitoring, then inspect node pools, VM and managed instance group health, and node logs when needed. | Use admitted Pod specs, admission errors, events, node labels, autoscaler visibility logs and Cloud Logging/Monitoring. Google owns host remediation. Neither mode gives customer access to control-plane hosts or etcd. [GKE observability](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/observability), [Autoscaler visibility](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/cluster-autoscaler-visibility) |
| Idle and small workloads | Billed for provisioned VMs, boot disks and networking even with idle Pods. Bin packing on already-paid nodes can lower marginal costs. | General-purpose Pod-based pricing follows billable admitted CPU, memory and ephemeral-storage requests. Specialized hardware can use whole-node pricing plus a management premium. Cluster fees, persistent storage, networking and observability have separate meters. [GKE pricing](https://cloud.google.com/kubernetes-engine/pricing) |
| NVIDIA GPUs | Run dedicated accelerator pools with explicit hardware, quotas, node identity, drivers, plugin ownership and autoscaling settings. | Select supported hardware through workload requirements. GKE provisions capacity and handles host integration. Verify version, machine shape, GPU count, sharing support and applicable billing model. [Standard GPUs](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/gpus), [Autopilot GPUs](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/autopilot-gpus) |

## Autopilot workloads in Standard

On supported versions and configurations, select a built-in Autopilot ComputeClass or a custom ComputeClass with Autopilot enabled. GKE manages the associated nodes and applies Autopilot admission and request rules to selecting workloads. General-purpose built-in classes use Pod-based billing. Explicit hardware rules can use node-based billing. Other pools keep Standard operations and pricing. A ComputeClass that enables only node pool auto-creation still creates Standard pools. Check prerequisites for the selected class and GKE build. [Autopilot mode in Standard](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-autopilot-mode-standard-clusters), [Setup and version requirements](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/autopilot-classes-standard-clusters)

For self-managed Kubernetes operators, the main operational shift is the failure boundary. GKE owns control plane recovery. Standard retains node pool design and host debugging, with Compute Engine quota and VPC IP allocation as additional failure points. Autopilot adds admission and managed provisioning to the scheduling path, so the submitted manifest, admitted Pod and provisioned capacity are three distinct inputs to an incident.

## Autopilot experiment outline

After Standard cleanup and separate approval, use one regional Autopilot cluster in `europe-west3`. Take a fresh inventory and check mode eligibility and rates first.

1. With no application replicas, record visible nodes, operations and workload capacity. Inspect workload identity configuration without granting IAM access.
2. Submit one small general-purpose CPU Deployment with deliberately undersized CPU/memory/ephemeral-storage requests. Compare its template and resulting Pod. Record effective requests and limits, provisioning time, scheduling events, node labels and billed resource dimensions. Check the detected compute class and bursting support before interpreting the result.
3. Use server-side dry-run on a standalone Pod with a privileged container and arbitrary host mount to inspect admission. Consider how a compliant DaemonSet would be defaulted and charged. Inspect cloud logs and events for both cases.
4. Scale the Deployment to zero and observe node visibility and eventual capacity reduction. Distinguish stopping general-purpose Pod charges from cluster fees and residual resources. Delete the approved lab cluster and verify cleanup independently with Compute and GKE inventory.

Learning check: Given a low-usage workload with inflated admitted requests, explain how HPA, placement and the Pod-based bill each respond.
